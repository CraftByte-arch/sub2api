## Why

当前新增的四类 usage 聚合都在 `usage_logs` 正常写入事务内同步更新，其中 Account 日统计平均每条日志会更新约四个聚合行，已经把 1C 数据库从稳定负载推向周期性满核。需要把这些自定义统计移出主写路径，同时保持现有页面、API 和精确统计语义不变，并继续把与上游代码的冲突面压缩在极少的稳定接入点。

## What Changes

- 新增统一但内部解耦的 usage 聚合 Repository 装饰层，四类统计仍由各自独立 Store 负责，原 Repository、Service 和 API 接口保持不变。
- 将统计读取改为“已关闭桶读聚合表 + 尚未关闭尾部读 `usage_logs` + 内存合并”，使跨日、跨小时和长请求仍能立即得到精确结果。
- 正常 `usage_logs` INSERT 不再同步更新自定义统计表；后台任务只聚合已经关闭的日桶或小时桶，并限制单次工作量、禁用并行查询、设置超时和跨实例维护锁。
- 为历史补写、UPDATE、DELETE 和保留期清理新增独立脏桶机制；正常写入当前开放桶不制造脏任务。
- 按风险从高到低逐项切换：先迁移 `account_usage_stats_daily`，生产观察后再迁移最近使用小时统计、普通用户首页日统计和 API Key 日统计。
- 使用只前进的新 migration 完成切换，不修改已经发布的 migration；部署采用“先兼容读、后卸载写触发器”的两阶段顺序。
- 不改变前端、HTTP 契约、筛选、精确总数、分页、导出、统计口径或请求完成时间分桶语义。

## Capabilities

### New Capabilities

- `custom-usage-aggregation-maintenance`: 为自定义 usage 聚合提供关闭桶维护、原始尾部精确合并、脏桶修复、受限后台执行及可安全分阶段切换的统一生命周期。

### Modified Capabilities

无。

## Impact

- Repository 新增组合装饰器、关闭桶维护协调器和各 Store 的混合读取/维护实现；最终只在原 Repository 构造处保留一个薄包装接入点，普通用户 usage 路由继续保留现有上下文标记。
- 数据库新增聚合水位和脏桶元数据，并通过新 migration 停用用户新增的同步聚合触发器；main 自带的分组汇总触发器保持不变。
- 第一批只切换 `account_usage_stats_daily`，其余三张表沿用当前行为，待 HC2 验证 CPU、WAL、写入延迟和统计差异后按同一机制逐项迁移。
- 回滚必须遵守两阶段兼容关系：卸载同步写入后只能回滚到已经支持“历史聚合 + 原始尾部”的兼容读取版本，不能直接回滚到只读整段聚合表的旧版本。
