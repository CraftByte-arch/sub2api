## Why

普通用户使用记录页每次应用筛选都会并发执行精确总数、统计卡片、模型分布、趋势和分组统计。HC2 上 `jixiwen2013` 的 2026-08-01 至 2026-08-31 数据显示，第一页明细仅需约 3ms，但上述统计会反复扫描约 18.5 万条 `usage_logs`，单条查询耗时约 1.2～7.9 秒并造成明显 IO 竞争。

项目需要持续同步和合并上游代码，因此优化必须保持页面功能和 API 契约不变，并把绝大多数实现放入新增文件，只保留极少的原代码接入点。

## What Changes

- 新增普通用户使用分析小时聚合表，按现有筛选维度同步维护精确请求数、Token、费用和时延指标。
- 新增独立 Repository 装饰器，在普通用户 `/usage` 请求上下文中优先读取聚合表；聚合未就绪、覆盖不足或筛选不支持时自动回退原 Repository SQL。
- 使用聚合表提供现有精确总数、统计卡片、模型分布、趋势、分组和入口 Endpoint 分布，保持响应结构和数值语义不变。
- 保留明细列表、排序、页码、深度分页和 CSV 导出的原有行为；明细行仍从 `usage_logs` 读取。
- 新增可恢复的分段回填、就绪状态和 INSERT/UPDATE/DELETE 增量维护，不修改现有 usage-log 写入代码。
- 前端、现有 API 路径、Handler/Service 公共接口和管理员统计路径保持不变。

## Capabilities

### New Capabilities

- `user-usage-filter-aggregation`: 为普通用户使用记录页提供精确、实时、可回退的筛选统计聚合能力，同时维持现有页面和 API 行为。

### Modified Capabilities

无。

## Impact

- 数据库新增小时聚合表、状态表、索引和 statement-level 触发器。
- Repository 新增独立装饰器、聚合查询 Store 和后台回填实现。
- 现有生产代码只增加用户 usage 路由上下文标记，并在 Repository 构造处包裹装饰器。
- 不修改前端页面、API 响应、管理员查询、CSV 导出格式或深度分页策略。
- 聚合启用后会增加一次按批次分组的同步 upsert 写入；需通过写入基准和生产回填节流控制影响。
