## Context

侧车在同步上游登录身份时已经读取了 Sub2API 的可用分组和分组倍率，以及 NewAPI 的用户分组数据。这些临时结果仅用于给同步到的 Key 推导倍率，随后即被丢弃，因此上游管理界面没有办法说明某个登录身份可使用的完整分组集合。

该变更只影响侧车。状态文件需要向前兼容已有快照，且一次上游分组请求失败时不能清空上一次成功得到的数据。

## Goals / Non-Goals

**Goals:**

- 为每个上游登录身份保存一份可用分组快照，包含名称、标识、平台类型、原始倍率、来源、同步时间和过期状态。
- 将快照通过现有上游管理 API 返回，并在前端以紧凑、可扫描的表格展示。
- 使用既有充值倍率换算函数计算最终倍率，且明确区分“未知”和数值零。
- 复用当前同步请求，不扩大主服务、数据库或上游请求范围。

**Non-Goals:**

- 不修改 Sub2API 主服务、账号计费或调度逻辑。
- 不从分组名称猜测平台类型，也不为动态 `auto` 分组伪造统一倍率。
- 不增加分组编辑、绑定或批量操作。

## Decisions

### 身份级分组快照

分组信息归属于登录身份，而不是上游站点。一个站点可登录多个账户，各账户的可见分组和用户覆盖倍率可能不同；因此 `UpstreamIdentity` 持有自己的分组 map。同步完整成功时原子替换快照，分组读取失败时保留旧快照并标记为过期。

替代方案是在 Key 上反推分组。该方案会遗漏没有 Key 的可用分组，且会把动态 Key 倍率错误地当成分组默认值，故不采用。

### 显式倍率语义

分组原始倍率与最终倍率均采用指针表示可用性。最终倍率只在充值倍率和分组倍率均存在时计算，采用现有 `recharge_rate.CNYPerUSD × group_multiplier` 公式。对动态或未提供倍率的分组保留空值和来源说明，不使用 `0` 代替。

替代方案是让前端自行计算。该方案会复制业务公式并造成不同页面结果不一致，故由 Manager 统一生成公开视图。

### 平台规范化与展示

后端仅规范化上游返回的明确值为 `openai`、`anthropic`、`gemini`、`grok`；未知值保持为空。前端用可访问的文字徽标显示类型，未知时显示“未知类型”，不依赖颜色作为唯一信号。表格沿用现有上游管理的紧凑数据密度和响应式收缩规则。

## Risks / Trade-offs

- [上游分组端点临时失败] → 保留已成功快照、标记“上次数据”，避免错误地显示没有可用分组。
- [NewAPI 不提供平台字段] → 显示“未知类型”，不作名称推断。
- [旧状态文件没有分组快照] → 加载时初始化空 map，首次同步后补齐；升级不会阻塞服务启动。
- [分组数量较多] → 表格仅在用户展开对应登录身份时渲染，并支持上游现有搜索筛选。

## Migration Plan

1. 将侧车状态版本升级并保持对旧版本的读取兼容。
2. 部署后不需要迁移脚本；下一次既有上游同步会填充分组快照。
3. 如需回滚，新字段会被旧版本忽略；不影响已有 Key、余额或登录材料。

## Open Questions

- 无。缺失的上游平台字段按“未知类型”展示是确定行为。
