## Context

侧车已经通过 `CoreClient.SetSchedulable` 调用 Sub2API 的管理员 HTTP 接口，并在自动检测状态机中使用 `ManagedSuspended` 标记“由侧车自动暂停”的账号。当前分组账号页面会展示调度状态和自动调度开关，但无法单独手动控制账号的全局 `schedulable` 状态。

本变更只部署在侧车中，不修改 Sub2API 主服务代码或数据结构。账号可能同时属于多个分组，因此手动调度开关天然是账号级全局操作，而不是当前分组内的局部操作。

## Goals / Non-Goals

**Goals:**

- 允许已通过管理员会话验证的用户，在侧车中手动停止或启用 API Key 账号调度。
- 保持“管理员手动停止”和“检测自动暂停”的状态归属清晰，避免健康检测错误恢复管理员手动停止的账号。
- 避免手动切换与正在执行的检测同时写入账号状态。
- 让没有检测配置的 API Key 账号也能使用手动调度开关。

**Non-Goals:**

- 不修改 Sub2API 的账号调度、重试或计费逻辑。
- 不为 OAuth 账号提供该开关。
- 不把全局调度开关改造成分组内局部绑定开关。
- 不新增数据库字段或外部依赖。

## Decisions

### 1. 复用现有 Sub2API 调度管理接口

侧车新增 `PUT /api/accounts/{accountID}/schedulable`，请求体仅接受 `{"schedulable": true|false}`。处理器调用引擎方法，引擎再复用现有 `CoreClient.SetSchedulable`，不触碰主服务代码。

备选方案是直接从前端调用 Sub2API 管理接口，但这会让浏览器承担主服务接口细节和权限边界，并绕过侧车状态机同步，因此不采用。

### 2. 手动操作接管暂停状态归属

手动切换成功后，若账号存在检测配置，侧车会更新账号快照、清除 `ManagedSuspended` 并清零连续成功/失败计数，但保留检测策略、下次检测时间、历史和最近错误。这样：

- 手动停止后，检测继续执行，但因为 `ManagedSuspended=false` 且主服务返回 `schedulable=false`，健康检测不会自动恢复账号。
- 手动启用曾被自动暂停的账号后，自动检测规则仍保持启用；未来重新达到失败阈值时仍可再次自动暂停。

备选方案是手动切换时同时关闭自动检测，但这会把两个独立控制混为一体，并中断管理员需要的持续观测，因此不采用。

### 3. 与检测共用账号级互斥占位

手动切换会在引擎的 `running` 映射中原子地检查并占用账号 ID，完成主服务调用和本地快照更新后再释放。若检测已运行则返回 `ErrAlreadyRunning`；若手动操作先占位，定时或手动检测也不会启动。

仅在调用前执行一次 `isRunning` 存在检查后启动检测的竞态，无法保证最后写入者，因此不采用。

### 4. 启用操作校验账号状态

仅 API Key 账号可操作。手动启用要求账号 `status=active`；手动停止允许对 API Key 账号执行，以便管理员在异常状态下仍能主动移除调度资格。主服务写入失败时不改变侧车持久化状态。

### 5. UI 明确区分两个开关

API Key 行操作列新增“账号调度（全局）”开关，并保留现有“自动调度”开关：

- 全局开关反映 `account.schedulable`。
- 自动调度开关反映健康检测是否接管。
- 停止前二次确认并说明影响所有分组。
- 自动暂停账号恢复前二次确认并说明自动规则仍可能再次暂停。
- 保存中、检测运行中和非 active 的启用操作不可用，并给出原因。

视觉复用现有开关、颜色、间距和动效，不引入新的设计语言。

## Risks / Trade-offs

- [账号状态可能被其他管理入口同时修改] → 每次操作前读取最新账号，并由后续总览轮询同步真实状态；侧车不宣称跨服务分布式锁。
- [手动停止后连续检测仍产生探测消耗] → 这是保持状态观测的既有目标，界面继续展示检测开关供管理员独立停用。
- [同一账号出现在多个分组时容易误解为局部操作] → 开关标题标明“全局”，停止确认框明确提示所有分组都会受影响。
- [调用主服务成功但本地状态保存失败] → API 返回失败并在下一次总览同步时按主服务真实状态修正；不进行可能反向覆盖管理员意图的自动回滚。

## Migration Plan

1. 发布包含新侧车 API、引擎方法和前端开关的版本。
2. 无需迁移数据；旧有账号和检测配置按原状态展示。
3. 如需回滚，仅回滚侧车版本；Sub2API 主服务及其账号数据不需要回滚。
